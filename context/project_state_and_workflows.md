# Weaver — Project State & Workflows

## Overview
Weaver is a visual front-end for Bright Data Scraper Studio: the user pastes a URL, sees the real page rendered (a sanitized, sandboxed live preview — not a flattened text list), clicks directly on the elements they want scraped, and Weaver turns that into a real Scraper Studio scraper (via the Bright Data CLI/API). When the target site's structure changes and extraction breaks, Weaver surfaces the self-healing repair as a reviewable diff (old vs. new selector/extraction) instead of a silent black-box fix, and lets the user approve/reject it.

**Status:** Day 2 of the hackathon. Repo just scaffolded. No code written yet.

## Technology Stack
- **Next.js (TypeScript), App Router, single full-stack web app.** Frontend (picker UI + healing-review dashboard) and backend (API routes shelling out to the Bright Data CLI) live in one codebase — chosen for solo-build speed and easy demo deployment.

## Core Product Flow (target design)
1. User pastes a target URL into Weaver's UI.
2. Backend fetches and sanitizes the page's real HTML (strips scripts/handlers, injects a `<base>` tag) and sends it to the frontend, which renders it in a sandboxed iframe — the real layout and CSS, not a flattened list. (Superseded an earlier "flattened text list" version — see "What Is Done" for why and what replaced it.)
3. User clicks the elements they want (e.g. title, price, rating).
4. Weaver turns the selection into a plain-English field description and calls `bdata scraper create <URL> "<description>"`, storing the returned Collector ID.
5. Weaver runs the scraper (`bdata scraper run`) on demand or on a schedule (via the Collector ID's `POST /dca/trigger` API), storing structured output.
6. Weaver watches run output for signs of breakage (nulls, missing fields, schema drift vs. prior runs) — this detection logic is ours, not Bright Data's.
7. On detected breakage, Weaver auto-triggers `bdata scraper heal <id> "<what broke>"`.
8. **"Review the fix" screen** (the UI differentiator): shows the heal command's before/after extraction side by side, lets the user Approve (`bdata scraper approve`) or Reject (`bdata scraper approve --reject`).
9. A running **healing activity log** per scraper: timestamped history of what broke, what was healed, and who approved it.

- **Picker UI, v2 (real sandboxed page preview) — replaces v1** (2026-08-19), after the user pushed back that a flattened list wasn't a close enough replica of the target site:
  - `src/lib/renderPage.ts` (replaces `parsePage.ts`) — fetches the real page and sanitizes it for safe embedding: strips `<script>` tags and inline `on*=` handlers, strips `<meta http-equiv="refresh">` and any CSP meta tag, strips nested `<iframe>`s, injects `<base href="{url}">` so every relative asset resolves back to the real site. `POST /api/render-page` (replaces `/api/parse-page`) wraps it.
  - `src/app/PagePicker.tsx` (new component) — renders the sanitized HTML via `<iframe srcDoc={html} sandbox="allow-same-origin">`. **The actual safety boundary is the missing `allow-scripts`** — none of the target page's JavaScript ever runs, in any origin; everything else in `renderPage.ts` is defense-in-depth on top of that, not the boundary itself. Candidate detection (the same tag set as v1: `h1–h4`, `p`, `li`, `td`/`th`, `a`, `span`, `div`, `img`, deduped, capped at 300 — now in `src/lib/pickerCandidates.ts`, shared/client-safe) runs client-side against the real rendered DOM via `querySelectorAll`, not a separately server-parsed copy, so what's clickable always matches what's visually on screen. Hover/click use event delegation with `closest("[data-weaver-id]")`; clicking calls back to `page.tsx` which keeps `selections` (id→label) as the source of truth, synced onto the iframe's DOM via a `weaver-selected` outline class whenever selections change (e.g. from the compact "Selected fields" list below the preview, which now just holds label inputs + remove buttons rather than the full row list).
  - **Known, accepted limitation, stated in the UI itself**: since scripts never execute, pages whose real content is rendered client-side (SPAs) will look incomplete. Server-rendered pages render close to as-is.
  - **Found and fixed two real timing bugs during verification — not assumed to work, actually driven through Playwright against the dev server and root-caused when it silently didn't**:
    1. Initially keyed candidate detection off the iframe's `load` event (both via React's `onLoad` prop and a manual `addEventListener`). It never fired — confirmed independently of our own code via `frame.waitForLoadState('load')` timing out while `domcontentloaded` resolved immediately. Root cause: `load` waits for *every* sub-resource to settle, and this environment's headless Chromium can't reach the open internet at all (a pre-existing, separately-confirmed limitation — real users' browsers won't have this problem), so external stylesheets/images hang indefinitely and `load` never fires. But the fix needed isn't environment-specific: any hanging third-party resource (analytics, fonts, ads) would cause the same silent failure for real users too. Fixed by switching to polling instead of waiting on `load`.
    2. The first version of that poll checked `readyState !== "loading" && doc.body` — but a transient blank `about:blank` document exists synchronously before the real `srcdoc` navigation completes, and it *already* satisfies that condition (readyState "complete", empty body present) — so the poll caught the blank document on its very first check and stopped looking, leaving `registryRef` permanently empty (candidates: 0) even though the real content loaded correctly moments later. Traced by logging `doc.body.innerHTML.length` at detection time (0, confirming the blank-doc theory) before fixing the condition to `doc.body.childElementCount > 0`, which only the real content satisfies.
  - **Re-verified after the fix, not just re-read**: confirmed 26 real candidates detected against `books.toscrape.com` (stable across repeated polls, not a fluke), then drove an actual click on the page's `<h1>` through Playwright and confirmed the click both (a) applied the ochre outline directly to that DOM element inside the iframe and (b) appeared correctly in the "Selected fields" panel below ("H1: A Light in the Attic", "1 field in the weave") — screenshotted as proof, not just asserted.
  - `npm run build` and `npm run lint` both pass clean after the rewrite; grepped for stray references to the removed `parsePage.ts`/`parse-page` route to confirm nothing was left dangling.

- **Visual design system, v2 — researched, not guessed** (2026-08-18): before rebuilding, actually researched real design teardowns (via `WebSearch`, not screenshots — headless Chromium in this environment can't reach the open internet, confirmed by testing against a trivial site; only `WebFetch`/`WebSearch` work) of Linear, Raycast, and Warp — the closest comparison class (developer tools known for *not* looking AI-generated). Common pattern across all three: dark-mode-first canvas (warmly tinted, not stark black), exactly **one** accent color used sparingly (not competing hues), Inter as the workhorse face (avoiding it isn't actually what makes these distinctive — restraint and detail discipline is), a dedicated monospace face for code/data, hairline 1px borders, small radii, **no gradients, no heavy shadows**. Full source list and findings relayed to the user in-chat.

Fixed by measuring the text's actual `scrollWidth` in a small `Typewriter` component (`useLayoutEffect` + a CSS custom property) and animating to that pixel value instead. Also split the original long tagline into a short animated hook + a calmer static subtitle, since forcing a long, wrapping sentence onto one `white-space: nowrap` line for the reveal trick was the wrong shape regardless.

- **✅ RESOLVED: `approve` was completing the review job without persisting the fix — root-caused and fixed** (2026-08-19):
  - Found via testing against the live Render deployment: created collector `c_mt003qmj16mt2cniaz` (description "book title and price") → healed it to add `star_rating` → `heal`'s `preview_result` correctly showed it → `approve` returned `status: "done"` → **but a subsequent `run` still didn't include `star_rating`, reproduced twice.**

  - **Fixed in `src/lib/brightdata.ts`**: `approveHeal` now always passes `--auto-save` on approval (not on rejection, where there's nothing to save). Comment in the code explains why, pointing back here.
  - **Re-verified through our own API routes locally**, not just the raw CLI: healed the same collector again (this time to add `availability`) via `POST /api/scrapers/[id]/heal`, approved via `POST /api/scrapers/[id]/approve`, and confirmed `POST /api/scrapers/[id]/run` now returns both `star_rating` and `availability`.
  - **Deployed and re-verified live on Render** (`c_mt00jee91kijwyx1sk`): baseline `run` returned only `book_title` → healed to add `price` → `approve` response included `"save_new_template"` in `completed_steps` → subsequent `run` correctly returned `price`. Confirmed against the actual production URL, not just localhost. This was caught and fixed *before* it reached the demo, not during it — worth remembering that Weaver's "review the fix" UI is only trustworthy because this got tested end-to-end against production.

Not a bug in our code; switched to a fresh collector to complete verification. Worth knowing for the demo: don't hammer heal requests back-to-back on the same collector.)

## Decisions Made So Far
- **Name:** Weaver.
- **Stack:** Next.js (TypeScript), App Router, single full-stack web app (not mobile, not a separate frontend/backend split).
- **Solo entry**, not a team.
- **Core differentiator:** making the self-healing repair reviewable/explainable via UI (approve/reject a diff), rather than a black-box "it just works" toggle — chosen because it hits Suit-Up (UI) and Reliability/Self-Healing judging criteria simultaneously, and because the official kickoff guide's own "bonus" suggestion ("automate the whole heal loop") implies most entrants will stop at full automation without a review layer.
- **Terminal/CLI-first build**, not dashboard-first — matches the grand-prize criterion on coding-agent integration and the official "keep the terminal as your UI" best practice.
- **Visual identity (v2, current)**: single dark theme, warm near-black canvas, one ochre accent (`--thread`), Inter + IBM Plex Mono — grounded in researched teardowns of Linear/Raycast/Warp rather than a generic "avoid AI-slop" checklist alone. Carry this system forward for the heal/review UI and activity log rather than improvising new styles.
- **Hosting: Render — live** at https://weaver-v4zo.onrender.com. Railway was ruled out (free trial expired); Render chosen for the same reason Railway was picked originally: persistent process, no serverless timeout to fight against 60–70s `create`/`heal` calls. Deployed and verified working end-to-end in production (see "What Is Done").
- Registration, Bright Data account signup, and starring the sponsor repo are already done (prerequisite steps, not project deliverables).
